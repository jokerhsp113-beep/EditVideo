# Updating the workflow from evidence

Use this cycle while executing an authorized editing task:

1. Record the actual failure and affected scene/timecode.
2. Decide whether the cause is project data, asset, engine or editorial guidance.
3. Apply the narrowest repair; do not add a universal rule for an isolated preference.
4. Verify the changed segment and any relevant regression cases.
5. Record before/after evidence, remaining limits and affected versions in the project's review history.

A faulty anchor resolver belongs in engine code and regression tests. An under-resolved image belongs in the asset/project decision. A repeated unmotivated pulse may justify changing a preset or an editorial rule. A user's preference for a calm evidence scene does not forbid lively hook scenes.

Keep stable operational rules in this skill, scenario-specific details in references, and subjective decisions with their examples. Remove superseded guidance when a replacement is verified. Updating these files changes future workflow context; it does not train model weights.

Run the skill validator after changing metadata or routing, and test observable behavior after meaningful code changes. Do not mark a case passed without execution. Routine editing does not create a background task or authorize publishing, purchasing or contacting others.
